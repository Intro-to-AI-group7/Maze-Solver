Maze-Solver 0.8.1

Maze-Solver 0.8.1 is a Java Swing desktop app for loading, visualizing, and solving grid mazes using DFS, BFS, Uniform Cost Search, Greedy Best-First Search, and weighted A*. Maze files support optional per-direction movement costs while preserving the original unweighted format.

It is designed for both interactive exploration and large-map performance testing, with a paint-based renderer that supports very large mazes efficiently.

Overview

Maze-Solver has six main responsibilities:

  1. Load human-readable .msmap maze files from disk.
  2. Validate and visualize the maze graph.
  3. Run DFS, BFS, UCS, Greedy Best-First Search, or weighted A* incrementally or instantly.
  4. Configure reproducible multi-algorithm experiment suites and export results.
  5. Review exact experiment maps in the animated renderer.
  6. Show traversal progress and final path with clear visual semantics.

Features

  • Title-screen startup flow with import-or-generate selection.
  • Random maze generation using traditional corridor carving.
  • Interactive solver controls for start, pause, restart, algorithm, and delay.
  • Instant solve mode that runs to completion in a background thread.
  • In-session map controls for loading a different map, saving the current map, and generating a new random map.
  • Paint-based grid rendering for all maze sizes.
  • Viewport clipping so only visible cells are painted.
  • Zoom controls (+/- and Ctrl + mouse wheel).
  • Gridline overlay for easier node-by-node visibility.
  • Start/goal color preservation after final path draw.
  • Debug diagnostics for maze import and neighbor consistency checks.
  • Optional weighted movement data using a compact [North, East, South, West] format.
  • Optional grid overlay for viewing directional movement costs. Equal opposite costs share one edge label; asymmetric costs show separate directional labels.
  • Default startup solve settings: A* algorithm and 200 ms step delay.
  • Application Settings can configure the maximum JVM heap for the next launch. Java cannot increase the heap limit of an already-running process; the launcher reads the saved setting and starts Java with the corresponding -Xmx option.
  • Configurable test-suite workflow from the title screen.
  • Seeded experiment generation with adjustable map size, interior obstacle density, reachability, endpoint placement, and movement-cost policies.
  • Generated experiment maps use a seeded traditional corridor-maze backbone. The configured blocked percentage is applied by opening additional cells or removing dead-end corridors, so density changes preserve long orthogonal walls and one-cell-wide passages instead of producing speckled noise.
  • Guaranteed-solvable generation retries disconnected layouts and uses a seeded winding connector only as a final fallback. Fixed endpoints are preserved during density adjustment.
  • Shared-map comparisons across any selected subset of the five algorithms.
  • Suite save/load, progress and cancellation, per-result animated review, suite map export, and UTF-8 CSV export.

Requirements

  • Java JDK 21 (LTS) or newer, including the jpackage tool for executable generation.
  • Windows, macOS, or Linux with desktop GUI support.
  • No external dependencies required.
  • Release version: 0.8.1 (also exposed by app.Version.RELEASE).

Quick Start

From the repository root:

  1. Compile (PowerShell)
New-Item -ItemType Directory -Force build\classes | Out-Null
$sources = @((Get-ChildItem -Filter *.java src -Recurse).FullName) +
@((Get-ChildItem -Filter *.java test\java -Recurse).FullName)
javac -Xlint:all -d build\classes $sources
  1. Run
java -cp build\classes app.MS

Run the dependency-free regression suite with:

java -cp build\classes test.RegressionTests

Run an experiment suite without opening Swing:

java -cp build\classes experiments.ExperimentCli `
--suite test\resources\suites\test_testSuiteExample.mstests `
--mode SEQUENTIAL `
--monitor-ms 1000 `
--csv build\results\cli-results.csv

The command-line runner prints periodic progress, heap usage, active worker counts, and interval worker peaks. Use FIXED_PARALLEL or ADAPTIVE_PARALLEL to benchmark the execution modes, and --repeat N to repeat the same seeded suite. Press Ctrl+C to request cooperative cancellation. Use --quiet when only the final timing summary is needed. This runner uses the same ExperimentRunner as the application, so command line runs exercise the production scheduler without UI rendering overhead.

Startup sequence:

  1. Title screen appears.
  2. Choose Import Maze or Generate Random.
  3. If importing, select a maze text file. If generating, enter rows and columns, then optionally enable movement weights with a range from 1 through 100.
  4. Solve interactively.

Use Back to Main Menu in the maze controls to leave an interactive session without exiting the application. The test-suite editor has the same navigation button, and closing either secondary window returns to the title screen. The title screen is hidden while a secondary screen is open so each menu is only shown once.

To configure experiments, choose Configure Tests on the title screen. Add one row per test condition, edit the row values, select algorithms and iterations, then choose Run Tests. Each generated-map iteration creates one map and uses that same map for every selected algorithm. Generated layouts retain the suite's row/column, blocked-percent, reachability, endpoint, seed, and movement-cost settings. Saved-map rows reuse their embedded map for every iteration. Automatic seeds are materialized when a suite is saved so later generated-map runs can be reproduced. Results can be exported manually or automatically to CSV, and unique maps can be exported for later inspection.

The test editor uses dropdowns for reachability, cost, endpoint, and map-source preferences. The Algorithms cell provides a checkbox multi-select, and boolean options use checkboxes. Numeric values are normalized to integers when editing ends. In RANDOM and DISTANCE endpoint modes, start and goal coordinates are disabled; DISTANCE enables the target-distance field.

Each row can use an automatic seed, a manually entered seed, or a saved map. Saved maps are imported through the row editor and embedded in the suite file using UTF-8-safe encoding, so the suite does not depend on the original map file remaining available. Saved-map results identify the source as SAVED_MAP and display N/A (saved map) instead of a generated seed. Test suites use the human-readable .mstests extension; individual maps use the human-readable .msmap extension. Import and save dialogs filter and normalize to their corresponding extension and open in the application directory. A saved suite contains applicationVersion=0.8.1 and version=1; the former identifies the application release and the latter is the stable suite schema version. Older schema-version-1 suites remain readable.

Before measured runs begin, the experiment runner performs a short JVM warm-up using each selected algorithm. Warm-up solves are excluded from the results, progress count, and timing metrics so class loading and JIT compilation are less likely to skew the first measured iteration.

Experiment suites run sequentially by default. Select Fixed parallel or Adaptive parallel in the test-suite editor to run independent algorithms for each generated map concurrently. Sequential mode remains available for compatibility checks and comparisons. Each generated map is shared by the selected algorithms for that iteration, and results remain ordered by test condition, iteration, and algorithm.

Parallel execution is most useful for larger maps or suites with several selected algorithms. Small suites may show little improvement because there is not enough work to keep all workers busy. Select Sequential to retain the original execution path for comparison and compatibility testing. Parallel execution improves throughput primarily for larger maps; small maps may show little memory or elapsed-time difference because they do not create enough work to saturate the workers.

Experiment results retain only measurements, configuration metadata, and the effective map seed. Generated maps are recreated from that seed only when a result is reviewed, which avoids retaining large serialized maps for every algorithm run. The results table is paged with selectable page sizes of 10, 25, 50, or 100 rows. The footer shows live JVM memory utilization, supports direct page-number entry, and supports jumps of 1, 10, or 100 pages in either direction. The progress status identifies the most recently completed test condition, and heap exhaustion reports the active condition so large suites can be split into smaller batches. Enable Follow latest results in the results footer to keep the table on the dynamically growing final page while a suite runs. Using any paging control pauses following so earlier result pages can be inspected; enable it again to resume following the newest page. The Results view selector can switch between the paged table and a live solve log. The live log appends each completed solve with its condition, iteration, algorithm, solved status, path cost, explored-node count, and runtime, and automatically follows the newest entry. It is intentionally bounded to the most recent 500 solve entries; the complete results remain available in the table and exported result data. The live log is split into a wide solver-activity pane and a narrower map-generation pane. The map pane records map readiness, solver dispatch, and map completion events, along with the number of generated maps currently loaded in memory waiting for solver work. That loaded-map count is distinct from maps still being generated and is also shown on the map progress bar. During a run, Pause cooperatively stops new map generation and solver work at task boundaries; Resume continues the same run. Cancel stops the run and clears retained maps, scheduler state, and completion queues so large generated maps can be reclaimed promptly. While solves are active, the log places live worker lines above the completed history and updates their nodes explored, current path cost, and elapsed time in place. Progress notifications are throttled so the diagnostic view does not receive one UI event per visited node. A future small-suite race view may make this comparison more visual.

Seed behavior is stable for the complete execution of each test case. Manual seed mode reuses the configured seed for every iteration, while automatic seed mode generates one seed once and reuses it for every iteration. Consequently, generated iterations in the same row recreate the same map; repeated solver runs are directly comparable rather than independent random samples. Saved-map mode reuses the embedded map and does not use a generated seed. Every selected algorithm in an iteration receives the same read-only map.

Approximate-distance endpoint selection first uses seeded random sampling for speed. If sampling misses a valid pair, the generator performs a deterministic distance-offset search before rejecting the layout. This keeps results reproducible while avoiding failures caused only by random endpoint sampling.

The test-suite results tab includes a Review button for each result. It reimports the exact map snapshot used by that result and opens the animated MazeRenderer with the result's algorithm selected. Export Maps creates a <suite-name>-maps folder under the selected directory and writes one complete saveable map file for each unique map. Repeated iterations are grouped in the filename, such as iterations-1-3, while distinct maps retain their iteration numbers. Seed-generated maps are converted into the same format used by imported maps, making them portable for later inspection or reuse.

How to Use

After loading or generating a maze:

  • Start: begin or resume timer-based solving.
  • Pause: stop solving without clearing current search state.
  • Restart: clear colors and reset the active algorithm state.
  • Load Map: replace the current session maze with another file.
  • Save Map: export the currently loaded maze to a text file.
  • Generate Map: create and load a new random maze without leaving the solver window.
  • Algorithm: choose DFS, BFS, Uniform Cost Search, Greedy Best-First Search, or weighted A*.
  • Step Delay (ms): set timer delay for step-by-step mode (1..5000).
  • Instant: solve to completion immediately (async worker).
  • Show Weights: overlay movement costs on grid edges. Labels appear when zoom is at least 20 pixels per cell and use a slightly larger font for readability. Equal opposite-direction costs use one number; different costs use direction markers (>, <, v, ^) and two numbers. During solving, labels next to visited nodes use a subdued gray style. Once solved, only the exact consecutive edges in the final path use an orange-on-gold highlight. Solver updates repaint only the changed cells and adjacent edge-label area; the entire grid is not redrawn for each visited node. The localized repaint includes a small pixel margin because labels are centered on cell boundaries.
  • Current Cost: the cost from the start to the most recently visited node. This tracks only that node's selected parent route, not all explored branches.
  • Final Cost: the total movement cost of the returned route, or -- when no solution has been found.
  • Solve Time: elapsed time spent inside solver search-step calls. Timer delays, UI repainting, and animation intervals are outside those measurements, so animated and instant solving times are directly comparable. The console also prints a diagnostic line containing the result, interval, algorithm, visited node count, final path cost, compute time, and wall-clock session time after each completed solve.
  • Zoom +/-: adjust cell size.
  • Ctrl + Mouse Wheel: zoom while cursor is over the maze viewport.

Saved maze files automatically receive a .msmap extension when one is not provided. The import dialog filters for .msmap maze files; reopening the dialog is sufficient to see a newly saved file, and restarting the application is not required.

Random generation details:

  • Uses a depth-first backtracking corridor-carving strategy for a classic maze look.
  • Keeps the outer border blocked.
  • Ensures the configured goal cell is connected to the carved maze.
  • Extends carving into final interior row/column on even dimensions to avoid persistent right/bottom wall strips.
  • The generator can optionally enable movement weights and accepts an inclusive minimum and maximum range from 1 through 100. These limits are centralized in Maze.MIN_MOVEMENT_COST and Maze.MAX_MOVEMENT_COST.
  • The default maximum in the generator dialog is 10.
  • The generator defaults to using the same positive integer cost in both directions of each connection. Clear the same-cost checkbox to generate independent integer costs for reverse directions.

Maze File Format

Expected format:

  1. Row count
  2. Column count
  3. start: row,col
  4. end: row,col
  5. One row per maze row using:
    • 1 for traversable/open
    • 0 for blocked/wall
  6. Optional WEIGHTS section with one four-value row per grid coordinate.

Example:

4
5
start: 3,0
end: 0,4
11111
10001
10101
11111

Legacy files without a WEIGHTS section remain valid. Every adjacent open-cell connection receives a default movement cost of 1.

There is one weight row for every coordinate in row-major order, including blocked cells. Each row is ordered [North, East, South, West] and uses:

  • 0: no permitted movement in that direction.
  • 1 or greater: the positive cost of moving in that direction.

For an open cell, a direction leading outside the maze or into a blocked cell must have cost 0. Blocked cells must contain four zero values. Costs may be asymmetric, so the cost from A to B does not have to equal the cost from B to A. The current map model preserves geometric neighbor references separately from movement availability: a neighboring node is traversable only when its movement cost is greater than zero.

MazeSolver uses movement costs when determining whether an edge is traversable and when calculating weighted search scores. UCS and A* guarantee a minimum-cost route when a route exists because all enabled movement costs are positive.

Validation rules enforced by import:

  • Dimensions must be positive.
  • Layout row count must match declared row count.
  • Each layout row width must match declared column count.
  • Only 0 and 1 are valid cell values.
  • Start and end must be in bounds and on traversable cells.
  • If WEIGHTS is present, it must contain exactly rows * columns rows.
  • Each weight row must contain exactly four integer values. Enabled movement costs must be in the range 1..100; 0 is reserved for disabled or non-existent directions.
  • Weight rows must match the layout topology.

Algorithms

The solver supports:

  • DFS: depth-first exploration, memory-light but not shortest-path or minimum-cost guaranteed.
  • BFS: breadth-first exploration, shortest by number of moves when all enabled moves have equal cost; it respects disabled edges but does not optimize weighted path cost.
  • Uniform Cost Search: uninformed priority search ordered by accumulated route cost g(n). With positive movement costs, it returns a minimum-cost path.
  • Greedy Best-First Search: priority search ordered only by the Manhattan heuristic h(n). It can explore fewer nodes, but it is not guaranteed to return a minimum-cost path.
  • A*: weighted informed search using cumulative directional movement costs and the Manhattan-distance heuristic. Since valid movement costs are at least 1, the heuristic remains an admissible lower bound and A* returns a minimum-cost path when one exists.

All algorithms use the [North, East, South, West] movement costs from the loaded maze. A neighboring cell with cost 0 is treated as an unavailable edge. A* stores cumulative costs as long values to avoid narrowing the sum of many individual movement costs.

A* heuristic used:

$$h(n) = |r_n - r_g| + |c_n - c_g|$$

where $r_n,c_n$ is current node and $r_g,c_g$ is goal.

The priority functions used by the informed searches are:

  • UCS: f(n) = g(n)
  • Greedy Best-First Search: f(n) = h(n)
  • A*: f(n) = g(n) + h(n)

The solver uses graph-search repeated-state tracking for all priority-based algorithms. UCS and A* ignore stale frontier entries after a cheaper route is discovered. Greedy keeps the first discovered route to each cell, consistent with its heuristic-only ordering and non-optimality guarantee.

The Manhattan heuristic is admissible because every enabled move costs at least 1. It is also consistent for this four-directional maze: moving to an adjacent cell changes Manhattan distance by at most 1, while the transition cost is at least 1.

Rendering and Performance

Current renderer behavior:

  • One paint-based path for every maze size.
  • Cell colors are cached in a backing array.
  • Only visible clip-region cells are painted each frame.
  • Gridlines are rendered with a subtle alpha stroke.
  • Start and goal labels (S/G) are drawn at larger zoom levels.

Color semantics:

  • Start: green
  • Goal: blue
  • Open: white
  • Blocked: dark gray
  • Visited: configurable (default yellow)
  • Final path: cyan

When the weight overlay is enabled, 0 means movement is disabled and positive numbers are movement costs. The overlay preserves directional asymmetry: for a horizontal connection, > is movement to the east and < is movement to the west; for a vertical connection, v is movement to the south and ^ is movement to the north.

After a solved run, start and goal are restored to semantic colors.

API and Extension Notes

Useful extension points:

Maze.Node start = maze.getStart();
MazeRenderer.setNodeColor(start, java.awt.Color.MAGENTA);
MazeRenderer.resetNodeColor(start);

Typical programmatic solve usage:

Maze maze = Maze.importFromFile(
"test/resources/maps/test_346x346.msmap");
Maze.Node next = maze.getStart().getNeighbor(Maze.Dir.EAST);
if (next != null && maze.getMoveCost(maze.getStart(), next) > 0) {
System.out.println("East movement is enabled.");
}
MazeSolver solver = new MazeSolver();
solver.setMaze(maze);
solver.setAlg("A*");
while (!solver.isFinished()) {
solver.updateSolve();
}
if (solver.isSolved()) {
java.util.List<java.awt.Point> path = solver.getFinalPath();
System.out.println("Path nodes: " + path.size());
System.out.println("Path cost: " + solver.getPathCost());
}

Troubleshooting

  1. App does not start
  • Confirm javac and java are on PATH.
  • Rebuild by compiling application sources in src\ and regression tests in test\java\ from the repository root.
  1. Maze fails to load
  • Check file format and dimensions.
  • Ensure start/end are on traversable cells (1).
  1. Slow behavior on huge maps
  • Use lower zoom to reduce overdraw.
  • Prefer Instant mode for completion-only runs.
  1. Unexpected debug output volume
  • The renderer prints diagnostics during load.
  • This is useful for validation but verbose on large maps.

Developer Notes: experiment execution

ExperimentRunner keeps the UI-independent execution path separate from Swing and preserves deterministic result ordering. Sequential mode executes one map and its algorithms directly. Fixed parallel mode uses the processor-aware worker cap; adaptive mode adjusts that cap from CPU load and heap headroom.

Parallel execution uses one priority executor. Map-generation tasks are prioritized while the memory frontier is open, but ready maps and queued solver tasks are bounded to approximately two worker-widths. This bound is important: queued solver tasks capture their shared map, so an unbounded queue would retain large maps even after generation has finished.

The coordinator is completion-driven. Worker completion releases a notification permit, avoiding fixed polling delays. A map is removed from scheduler state after its final selected algorithm completes; the resulting ExperimentResult contains measurements and metadata, not the map object. Clearing scheduler collections during cancellation and shutdown makes those maps eligible for garbage collection promptly. The JVM may retain committed heap for reuse, so process working-set size is not the same as live object usage.

Admission reservations estimate map cells, solver tables, and transient solver overhead with a safety factor. They are a scheduling guard, not a heap measurement. Diagnostics therefore expose both reservation state and JVM heap state. On hybrid CPUs, Runtime.availableProcessors() reflects processors exposed to the JVM; process affinity can be used for controlled comparisons.

Debug mode opens a terminal window while the application runs. Building it requires JDK 21 or newer, jpackage, and the .NET 8 SDK for the native self-extractor wrapper.

On Linux, make the equivalent scripts executable once and run:

chmod +x scripts/compile-and-run.sh scripts/build-executable.sh

These bundles include the Java runtime and do not require Java to be installed on the target machine. The generated build/ and dist/ directories are ignored by Git.
